# 플레이어 상태별 테스트 전략

## 목적

이 문서는 Sheepy 자동화 QA에서 플레이어 상태를 어떻게 나누어 TC에 반영할지 정의한다.

같은 게임 실행 테스트라도 처음 플레이하는 사용자와 이미 플레이 기록이 있는 사용자는 초기 화면, 세이브 데이터, Continue 표시, 튜토리얼 노출 여부가 달라질 수 있다.

따라서 TC를 작성할 때 기능 대분류만 보지 않고, 플레이어 상태를 함께 기록한다.

## 기준

ISTQB Foundation 관점에서는 사전조건, 테스트 데이터, 기대결과가 달라지는 경우 별도 테스트 조건으로 분리해야 한다.

ISTQB Game Testing 관점에서는 저장/로드, 튜토리얼, 첫 진입 경험, 진행 상태 복구가 게임 품질에 직접 영향을 준다.

## 플레이어 상태 구분

| 상태 ID | 상태 이름 | 설명 |
| --- | --- | --- |
| PLAYER-NEW | 최초 실행 유저 | 세이브 데이터나 진행 기록이 없는 상태 |
| PLAYER-RETURNING | 기존 플레이 유저 | 세이브 데이터나 진행 기록이 있는 상태 |
| PLAYER-UNKNOWN | 상태 불명확 | 자동화가 세이브 데이터 유무를 아직 판별하지 못한 상태 |

## 상태별 주요 차이

| 구분 | 최초 실행 유저 | 기존 플레이 유저 |
| --- | --- | --- |
| 초기 화면 | New Game, 시작 안내, 튜토리얼 가능성 | Continue, Load, 기존 진행 상태 가능성 |
| 테스트 데이터 | 깨끗한 세이브 상태 필요 | 특정 세이브 상태 또는 기존 진행 기록 필요 |
| 기대결과 | 첫 진입 흐름이 정상적으로 보여야 함 | 이어하기 또는 저장 상태 복구가 가능해야 함 |
| 주요 리스크 | 튜토리얼 미노출, 새 게임 시작 불가 | Continue 불가, 저장 데이터 손상, 잘못된 위치 복구 |
| Evidence | 세이브 데이터 없음 증거, 첫 화면 screenshot | 세이브 데이터 있음 증거, Continue 화면 screenshot |

## TC 작성 시 반영 방식

각 TC는 필요한 경우 다음 항목을 추가한다.

| 항목 | 설명 |
| --- | --- |
| 플레이어 상태 | PLAYER-NEW, PLAYER-RETURNING, PLAYER-UNKNOWN 중 하나 |
| 테스트 데이터 | 세이브 데이터 없음, 특정 세이브 데이터 있음 등 |
| 상태 준비 방법 | 세이브 파일 삭제, 테스트용 세이브 파일 배치, 기존 상태 유지 등 |
| 상태 복구 방법 | 테스트 후 세이브 백업 복원 또는 변경 없음 |

## 적용 우선순위

초기 Sprint에서는 세이브 파일을 직접 수정하지 않는다.

먼저 현재 실행 환경에서 관찰 가능한 상태를 `PLAYER-UNKNOWN`으로 기록하고, 이후 세이브 경로와 백업/복원 방식이 확인되면 `PLAYER-NEW`와 `PLAYER-RETURNING`을 분리한다.

## 우선 추가할 TC 후보

| 후보 TC | 플레이어 상태 | 목적 |
| --- | --- | --- |
| TC-014 최초 실행 상태 식별 | PLAYER-NEW | 세이브 데이터가 없는 상태에서 첫 진입 화면을 확인 |
| TC-015 기존 플레이 상태 식별 | PLAYER-RETURNING | 세이브 데이터가 있는 상태에서 Continue 또는 진행 상태 표시를 확인 |
| TC-016 세이브 상태 보존 확인 | PLAYER-RETURNING | 테스트 실행 후 기존 세이브 데이터가 변경되거나 손상되지 않았는지 확인 |

## 현재 제한

- Sheepy의 세이브 파일 경로와 구조를 아직 프로젝트에서 확정하지 않았다.
- 세이브 데이터를 자동으로 삭제하거나 덮어쓰는 테스트는 사용자 데이터 손상 위험이 있으므로 바로 구현하지 않는다.
- 세이브 상태를 다루는 TC는 백업/복원 기준을 먼저 문서화한 뒤 구현한다.
