# Sprint 분리 기준

## 목적

이 문서는 Sheepy 자동화 QA에서 Sprint를 어떤 기준으로 나누었는지 설명한다.

이번 프로젝트는 실제 Steam 게임을 대상으로 하므로, 게임 진입부터 게임 진행 테스트까지 한 번에 묶지 않는다.

대신 실패 원인을 분리하기 쉽고, evidence를 명확히 남길 수 있는 작은 단위로 Sprint를 나눈다.

## 기준 요약

Sprint 분리 기준은 다음과 같다.

| 기준 | 설명 |
| --- | --- |
| 선후관계 | 앞 단계가 성공해야 뒤 단계 테스트가 의미 있는가 |
| 실패 원인 분리 | 실패했을 때 환경, 제품, 테스트 코드 문제를 좁혀 볼 수 있는가 |
| Evidence 명확성 | screenshot, process state, log 등으로 근거를 남길 수 있는가 |
| 자동화 난이도 | 너무 많은 자동화 난이도를 한 Sprint에 몰아넣지 않는가 |
| ISTQB 연결성 | ISTQB Foundation과 ISTQB Game Testing 기준에 연결되는가 |

## 전체 흐름

```text
환경 확인
↓
실행 확인
↓
화면 관찰
↓
입력 반응
↓
플레이 흐름
↓
안정성
↓
Evidence / 리포트
```

이 순서는 단순한 게임 진행 순서가 아니다.

테스트 가능 조건의 의존 관계와 실패 원인 분리 가능성을 기준으로 정한 순서이다.

## Sprint 1: 실행 환경과 초기 진입

목표는 Steam과 Sheepy를 자동화 대상으로 사용할 수 있는 최소 조건을 확인하는 것이다.

확인 질문:

- Steam이 설치되어 있거나 실행 중인가?
- Sheepy AppID 실행 명령을 호출할 수 있는가?
- Sheepy 프로세스를 감지할 수 있는가?
- 초기 화면 screenshot을 저장할 수 있는가?

이 단계가 필요한 이유:

Steam 실행이나 프로세스 감지가 되지 않으면 화면 테스트, 입력 테스트, 플레이 테스트는 의미가 없다.

ISTQB 연결:

| 기준 | 연결 |
| --- | --- |
| Foundation | 테스트 환경, 사전조건, 테스트 베이시스 |
| Game Testing | 플랫폼 리스크, 게임 제품 리스크 |

## Sprint 2: 화면 상태 판별

목표는 단순히 screenshot을 저장하는 것을 넘어, 화면이 테스트 가능한 상태인지 판단하는 것이다.

확인 질문:

- 화면이 검은 화면으로만 유지되지 않는가?
- 초기 화면 또는 메인 메뉴로 보이는 상태에 도달했는가?
- screenshot을 기준으로 화면 상태를 설명할 수 있는가?

이 단계가 필요한 이유:

화면 상태를 판별하지 못하면 입력 반응 테스트에서 입력이 문제인지, 화면이 준비되지 않은 것인지 구분하기 어렵다.

ISTQB 연결:

| 기준 | 연결 |
| --- | --- |
| Foundation | 관찰 가능한 기대결과 |
| Game Testing | Graphics Testing |

## Sprint 3: 입력 반응

목표는 키보드 입력이 게임 화면 변화로 이어지는지 확인하는 것이다.

확인 질문:

- 점프 입력 전후 화면 차이가 있는가?
- 좌우 이동 입력 전후 화면 변화가 있는가?
- 입력 대상 창이 올바르게 활성화되어 있는가?

이 단계가 필요한 이유:

화면이 준비된 상태를 확인한 뒤에야 입력 반응을 검증할 수 있다.

ISTQB 연결:

| 기준 | 연결 |
| --- | --- |
| Foundation | 입력값과 기대결과 |
| Game Testing | Game Controllers Testing, Game Mechanics Testing |

## Sprint 4: 기본 플레이 흐름

목표는 새 게임 시작 후 짧은 플레이 구간이 진행 가능한지 확인하는 것이다.

확인 질문:

- 새 게임 또는 Continue로 플레이 상태에 진입할 수 있는가?
- 이동과 점프를 조합해 짧은 구간을 진행할 수 있는가?
- 진행 불가 상태에 빠지지 않는가?

이 단계가 필요한 이유:

입력 반응이 확인된 뒤에야 여러 입력과 화면 전환이 묶인 플레이 흐름을 검증할 수 있다.

ISTQB 연결:

| 기준 | 연결 |
| --- | --- |
| Foundation | 시나리오 테스트, 상태 전이 |
| Game Testing | Game Mechanics Testing, Game Level Testing |

## Sprint 5: 안정성 관찰

목표는 게임이 일정 시간 동안 비정상 종료되거나 멈추지 않는지 확인하는 것이다.

확인 질문:

- 일정 시간 동안 프로세스가 유지되는가?
- 화면 변화가 장시간 멈추지 않는가?
- 짧은 플레이 중 크래시가 발생하지 않는가?

이 단계가 필요한 이유:

실행 직후의 안정성보다 실제 플레이 상태에서의 안정성 관찰이 더 의미 있다.

ISTQB 연결:

| 기준 | 연결 |
| --- | --- |
| Foundation | 리스크 기반 테스트, 신뢰성 |
| Game Testing | 게임 제품 리스크, 기술 리스크 |

## Sprint 6: Evidence와 리포트

목표는 각 TC 실행 결과를 사람이 확인하기 좋은 형태로 정리하는 것이다.

확인 질문:

- 실패 시 screenshot, process state, log가 저장되는가?
- 실행 결과를 JSON 또는 Markdown으로 요약할 수 있는가?
- 실패 원인을 제품, 테스트, 환경, 검토 필요로 나눌 수 있는가?

이 단계가 필요한 이유:

자동화 테스트는 실행만으로 끝나지 않고, 실패를 재현하고 설명할 수 있어야 한다.

ISTQB 연결:

| 기준 | 연결 |
| --- | --- |
| Foundation | 테스트 실행 결과 기록, 결함 보고 |
| Game Testing | 게임 결함 재현과 증거 확보 |

## Sprint를 이렇게 나눈 이유

뒤 단계일수록 앞 단계에 의존한다.

예를 들어 Steam 실행이 안 되면 화면 테스트를 할 수 없다.

화면 캡처가 안 되면 입력 전후 비교를 할 수 없다.

입력 반응이 확인되지 않으면 기본 플레이 흐름 테스트가 의미를 잃는다.

따라서 Sprint는 다음 원칙으로 나눈다.

```text
앞 단계 실패 원인을 제거한 뒤
다음 단계의 테스트 조건을 만든다.
```

## 하네스와 루프를 처음부터 넣지 않는 이유

이번 프로젝트는 하네스와 루프가 항상 필요한지 확인하기 위한 비교 목적도 가진다.

따라서 초기 Sprint에서는 일반 자동화 QA 방식으로 진행한다.

반복 코드, 대기 불안정, evidence 저장 중복, 실패 원인 분리 어려움이 실제로 나타날 때 하네스 또는 루프 도입을 검토한다.

## 결론

Sprint 분리 기준은 기능 구현 순서가 아니라 다음 기준의 조합이다.

- 테스트 가능 조건의 선후관계
- 실패 원인 분리 가능성
- evidence 명확성
- 자동화 난이도
- ISTQB 기준 연결성

이 기준을 통해 각 Sprint는 독립적으로 실행하고, 실패했을 때 다음 단계로 넘어가기 전에 원인을 확인할 수 있게 한다.
