# 테스트 기준과 적용 원칙

## 목적

이 문서는 `Sheepy_QA_Python` 프로젝트에서 테스트를 어떤 기준으로 설계하는지 정의한다.

모든 테스트 케이스는 이 문서를 기준으로 대분류, 소분류, 테스트 조건, 기대결과, evidence를 연결한다.

## 참조 기준

### ISTQB CTFL Foundation Level

Foundation 기준은 테스트 설계의 기본 흐름을 잡는 데 사용한다.

이 프로젝트에서는 다음 개념을 적용한다.

| 기준 | 적용 방식 |
| --- | --- |
| 테스트 베이시스 | Steam 페이지, 실제 게임 실행 화면, 조작 방식, 관찰 가능한 결과 |
| 테스트 조건 | 검증할 동작 또는 품질 조건을 한 문장으로 정의 |
| 테스트 케이스 | 사전조건, 입력, 절차, 기대결과, evidence로 구체화 |
| 기대결과 | PASS/FAIL 판단 기준을 사전에 고정 |
| 추적성 | 기준, 대분류, 소분류, TC를 연결 |
| 리스크 기반 우선순위 | 실행 불가, 입력 무반응, 진행 불가, 크래시처럼 영향이 큰 항목 우선 |

### ISTQB CTFL Game Testing

Game Testing 기준은 게임 QA 특화 대분류를 잡는 데 사용한다.

이 프로젝트에서는 다음 개념을 적용한다.

| 기준 | 적용 방식 |
| --- | --- |
| Game Testing Basics | 단순 플레이와 테스트 활동을 구분 |
| Game Product Risks | 실행 실패, 화면 멈춤, 입력 무반응, 진행 불가, 크래시 리스크 도출 |
| Game Mechanics Testing | 이동, 점프, 상호작용 같은 기본 플레이 동작 확인 |
| Graphics Testing | 화면 표시, 검은 화면, 깨짐, UI 표시 문제 확인 |
| Sound Testing | 초기 범위에서는 제외하고 후속 확장 후보로 둠 |
| Game Level Testing | 첫 구간 진입과 진행 가능성 확인 |
| Game Controllers Testing | 초기에는 키보드 입력, 후속으로 컨트롤러 확장 |
| Localization Testing | 초기 범위에서는 제외하고 후속 확장 후보로 둠 |

## 테스트 베이시스

이번 프로젝트는 제품 내부 요구사항 문서를 가지고 있지 않다.

따라서 테스트 베이시스는 다음 자료와 관찰 결과를 사용한다.

- Steam Store의 게임 정보
- 게임 실행 후 확인한 실제 화면
- 사용자가 직접 확인한 기본 조작 방식
- Windows 프로세스 상태
- 스크린샷과 화면 변화
- 자동화 실행 로그

## 테스트 설계 원칙

1. 테스트 목적을 먼저 정의한다.
2. 테스트 기준을 문서에 남긴다.
3. 대분류와 소분류를 정한 뒤 TC를 작성한다.
4. 각 TC는 하나의 주요 판단 목적을 가진다.
5. 기대결과는 테스트 실행 전에 고정한다.
6. 자동화 실패를 곧바로 제품 실패로 단정하지 않는다.
7. evidence가 부족하면 `REVIEW_REQUIRED`로 남긴다.

## 실패 분류 기준

| 분류 | 의미 |
| --- | --- |
| `PRODUCT_FAIL` | 게임의 기대 동작과 실제 동작이 다름 |
| `TEST_FAIL` | 자동화 코드, 입력 방식, 이미지 기준, 테스트 절차 문제 |
| `ENV_FAIL` | Steam 미실행, 게임 미설치, 실행 권한, 해상도, OS, 프로세스 문제 |
| `REVIEW_REQUIRED` | 실패는 발생했지만 판단 근거가 부족함 |

## 이번 프로젝트의 핵심 질문

- 내부 상태 접근 없이 자동화 QA를 어디까지 할 수 있는가?
- 하네스 없이 작성한 테스트는 언제 중복되거나 불안정해지는가?
- 루프 엔지니어링은 어떤 테스트에서 실제로 필요한가?
- 게임 QA에서 TC 대분류와 소분류는 어떤 기준으로 나누는 것이 좋은가?
