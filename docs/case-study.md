# 사례: 화면 사전조건과 잘못된 성공 판단

## 관찰한 문제

과거 실행에서 Space 입력 후 화면이 바뀌어 후속 TC가 REVIEW_REQUIRED로 끝났다. 이는 현재 [과거 이력](history/2026-09-13-before-revision.md)에 남아 있다. 테스트 순서가 제품 실패처럼 보일 수 있으므로 시작 상태를 독립적으로 확인할 필요가 있었다.

추가 코드 검토에서 TC-016은 같은 이미지를 자기 자신과 비교해 변화량 0을 만들고, 변화량 >=0.05를 요구하는 플레이 후보 판정에 전달하고 있었다. 이 구조로는 해당 진입 조건을 충족할 수 없었다. 실제 게임 버그가 아닌 자동화 사전조건 결함이다.

## 변경

screen_preparation은 LANGUAGE→LOBBY→GAMEPLAY 후보의 관찰/Enter/제한시간을 분리했다. local_screen_session은 실제 로비 이미지와 전환 후 이미지를 비교한다. TC-006/010/011/016/018/019에 연결했고 입력마다 foreground를 다시 확인한다.

## 재현·검증 근거

단위 테스트에서 준비 완료 시 무입력, 언어 선택 정체 시 Enter 1회, 검은 화면 회복, 포커스 상실 중단, 알 수 없는 화면 중단을 검증한다. 실제 게임 반복 검증은 별도 필요하며 단위 테스트로 해결됐다고 단정하지 않는다.

추가 판정 회귀: 빈 expectedSignals의 PASS를 REVIEW_REQUIRED로 변경. 초반 화면 변화가 이후 10초 무변화를 덮지 않도록 연속 구간을 기록. 저장 경로 유지의 상태명을 SAVE_FILES_PRESENT로 제한했다.

## 남은 확인

실제 환경에서 로비 시작 3회 실행, 준비 전후 화면, 입력 효과를 사람이 대조해야 한다. 이미 플레이 중인 임의 화면에서 로비로 복귀하는 기능은 없으므로 각 입력 TC는 수동 로비 준비가 필요하다. [실행 계획](sprint-plan.md)

## 실제 재현: 로비 전환 중 후보 조기 수락

2026-09-14 TC-010은 Enter 후 0.812초에 GAMEPLAY 후보로 PASS했지만 저장 화면에는 로비 타이틀이 남아 있었다. raw PASS는 보존하고 실제 플레이 진입 완료로 인정하지 않는다. 준비 절차에서 후보를 2초 연속 관찰하도록 보완하고 검은 화면·로비 재관찰 시 시간을 초기화한다. 순간 후보→검은 화면 반례를 단위 테스트로 재현했다. 이 완충 시간도 플레이 화면의 의미를 증명하지 않으므로 실제 화면 대조와 다양한 전환 표본 평가가 필요하다.

후속 실제 TC-006은 2초 유지 보완 후에도 로딩 중 입력하여 FAIL(delta=-0.118)했다. 증거에 제목 표시줄이 포함되어 검은 화면의 어두운 픽셀 비율을 낮추는 것을 확인했다. 창 외곽 좌표 대신 실제 관찰한 NW.js 렌더링 자식 창(Chrome_RenderWidgetHostHWND)의 좌표로 640×360 게임 영역만 캡처하도록 수정한다. 창 영역 취득 실패 시 전체 바탕화면으로 대체하지 않는다. 임계값은 변경하지 않았다. 기존 외곽 이미지와 새 client 이미지의 좌표 기준이 달라지므로 이미지 판정은 재검증해야 한다.

일반 GetClientRect도 NW.js의 사용자 지정 제목 표시줄을 포함하는 것을 확인했다. 렌더링 자식 창이 정확히 하나이며 부모 창 안에 있을 때만 캡처한다. 그렇지 않으면 오류로 중단한다.

수정 후 TC-006은 로딩 검은 화면을 인식해 입력 전에 REVIEW_REQUIRED로 중단했다. 이 환경의 Continue 흐름에서는 Enter 이후 BLACK 관찰을 거친 뒤 GAMEPLAY 후보가 2초 유지돼야 준비 완료로 인정하도록 보수적으로 제한했다. 로딩 프레임을 놓치면 성공으로 추정하지 않고 보류한다. 다른 빌드나 즉시 전환 흐름에는 추가 프로필 검증이 필요하다.
